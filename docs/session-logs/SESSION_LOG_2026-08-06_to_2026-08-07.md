## 1. Accrued Interest — legacy (migrated) loans excluded, now included

User reported the "Accrued interest" card missing on a matured loan's page for some loans. Root
cause: `GetAccruedInterestUseCase` returned `null` unconditionally for any loan with a `legacyId`,
but `resolveComputedPenalty` already falls back to the migrated `due.penalty` snapshot for a
non-prospective loan — no technical reason to skip the accrual figure itself. Live data check: 1,200
of 1,201 currently-"Matured" loans are legacy, so this was a broad, real gap.

- `GetAccruedInterestUseCase.ts`: removed the `legacyId` early-return; `isProspectiveLoan` now
  derives from `!loanAccount.legacyId` (previously hardcoded `true`), so the penalty half of the
  formula still uses the right basis per loan type.
- Verified against a real legacy matured loan (`SL-LAZ_B5A3P`) — correct nonzero accrual.

## 2. Statement of Account (SOA) — a long series of print/UX fixes

All changes to `templates/SOA.docx` (via direct OOXML edits + `pizzip` repack, verified each time
via LibreOffice headless PDF conversion) and `StatementOfAccountMergeDataResolver.ts`.

- **Remaining Amortization table font** — was 5pt cells / 7pt heading (illegible when printed).
  Bumped to 9pt / 10pt, matching the rest of the document.
- **Column wrapping** — the font bump caused digits to wrap onto two lines at the old (narrow)
  fixed column widths. Widened columns (later narrowed again per #7 below), and separately found
  the *actual* driver of the wrap was row height from font size, not spacing — a red herring
  investigated and ruled out along the way (TableGrid style already zeroes paragraph spacing).
- **Comma-formatted amounts** — new `formatMoney()` helper (scoped to this resolver only —
  `Money.toString()` itself stays machine-parseable for every other consumer) adds thousands
  separators to every peso figure on the printed SOA.
- **Remaining Amortization hidden once matured** — added a `ShowRemainingSchedule` merge flag
  (loan not yet past its last installment's due date as of the statement date) and a
  `{#ShowRemainingSchedule}` docxtemplater conditional wrapping the whole section — a matured
  loan's remaining-installment table is redundant with the Past Due section above it.
- **Penalty date: single "as of" vs. range** — a prospective loan's "Penalty {From} / {To}" implied
  staff picked a real range, when only "To date" (the form's "As of date") is ever user-entered.
  Added an `IsProspectiveLoan` flag + `{#IsProspectiveLoan}`/`{^IsProspectiveLoan}` conditional:
  prospective loans print "Penalty {ToDate}" (matches Accrued Interest's own pattern); migrated
  loans keep the real From/To range (genuinely both staff-entered there).
- **Blank dates when amount is zero** — `PenaltyFromDate`/`PenaltyToDate` and (added later, same
  rule) `AccruedInterestAsOfDate` all blank out when their respective amount is `.isZero()` — a
  printed date next to ₱0.00 read as if something had accrued over that period.
- **Single page fit** — the font/column changes grew row height enough that a 12-installment loan
  with a co-borrower spilled onto a near-empty page 2. Fixed via bottom margin 720→300 twips and
  document-wide default paragraph spacing-after 160→40 twips (spacer paragraphs only — table
  content already used TableGrid's own zero spacing).
- **Narrower Remaining Amortization columns** (follow-up, user request) — the column headers
  ("Principal", "Interest", "Total due") were already wider than any real figure in them. Kept Due
  Date fixed-but-tight (2000 twips, fits "September 4, 2026" with no wrap) rather than true
  Word/LibreOffice autofit — user's own call after being warned autofit was what caused the earlier
  wrap bug. Other three columns 1900→1400 twips each (7900→6200 total).
- **Co-Borrower fallback** — Co-Borrower/Address printed blank despite one on file. Root cause:
  two non-overlapping linkage mechanisms exist (`loanAccount.coBorrowerIds` per-loan join vs. a
  per-borrower direct attachment from Client Profile's "Add Co-Borrower," ADR-015) and this
  resolver only checked the first. Added the same loan-then-borrower fallback
  `LoanDetailPage.tsx`'s e-signature default-fill already uses. Verified against the real reported
  loan (`SML-REG_00381`).
- **"Scroll more" hint on the Create SOA dialog** — the dialog's content can run taller than the
  viewport with no visual cue. Bottom fade + "Scroll more" chip, sticky within `DialogContent`
  itself (the dialog's own scroll container), hidden once scrolled to the bottom. Mockup approved
  first.
- Six test SOAs generated during this session's own testing (`SML-REG_00381`, SOA-00001 through
  -00006) were deleted at user's explicit request/permission — DB rows + their storage PDFs.

## 3. Report date-range filter — Manila calendar day, not UTC

User reported: filtering the Transaction Report to Aug 4–6 excluded a payment whose value date was
genuinely Aug 4. Root cause: date-only fields (a payment's value date, etc.) are stored as that
Asia/Manila calendar day's UTC-shifted midnight (e.g. `2026-08-03T16:00:00Z` = Manila Aug 4 — same
convention already used for SMS/email reminders), but `reportingController.ts`'s `parseDate()`
parsed "from"/"to" as literal UTC midnight — 8 hours after the Manila day actually starts, silently
excluding early-Manila-day records.

- Extracted the existing `manilaDayRange()` helper (previously duplicated verbatim in
  `PrismaSmsReminderRepository` and `PrismaEmailReminderRepository`) into a shared
  `src/shared/domain/manilaTime.ts`; both repositories now import it instead.
- `parseDate()` now resolves "from" to the Manila day's start and "to" to its last instant — fixes
  every report using the shared `entryDateFilter()`/`filter.from`/`filter.to` path: Loan
  Origination, Collection, Transactions, Releases, Accounts With Past Due, Collection History,
  Expected Collection, First Amortization, Daily Collection, Fully Paid Accounts.
- Verified live: the reported Bayron `REPAYMENT` (excluded before, included after) via a real API
  call against the running container.

## 4. Transaction Report — scroll/UX overhaul

- Wrapped the table in a fixed-height (~25 rows) scrollable container instead of one ever-growing
  page; sticky header, sticky Total row (per user follow-up — stays visible, doesn't scroll away).
- **Found and fixed a real bug along the way**: the sticky header/footer didn't actually stick.
  Root cause — the shared `Table` component always wraps its `<table>` in its own `overflow-auto`
  div (for horizontal scroll), which sat *between* the page's own scroll box and the sticky
  thead/tfoot, becoming a competing scroll-positioning ancestor even though it never itself
  scrolled vertically. Added an optional `containerClassName` prop to `Table` (default unchanged,
  every other page unaffected) so this page can neutralize that inner wrapper and have exactly one
  scrolling ancestor.
- Added a bottom fade + "N more below" scroll-hint chip (mockup approved first), tracked via a
  scroll listener computing remaining rows from `scrollHeight`/`scrollTop`/`clientHeight`.

## 7. PDF preview — download filename now correct

User reported: downloading from inside the document/SOA preview gave a different (generic) filename
than the app's own Download button (which correctly applies `buildDocumentFileName()`). Root cause:
the preview `<iframe>`'s `src` is a `blob:` URL, rendered by Chrome's *own* built-in PDF viewer
toolbar (with its own Download button that saves the raw blob directly, bypassing the app's naming
entirely). Appended the `#toolbar=0` PDF open parameter to hide that built-in toolbar — the
component's own (correctly-named) Download button is now the only way to download from preview.

## 8. Sidebar navigation — scroll position now resets

User reported: switching sidebar menus kept the previous page's scroll position instead of landing
at the top. Root cause: `<main>` (not window/document) is `AppLayout`'s actual scroll container, by
design (sidebar and main content scroll independently), and React Router has no built-in scroll
reset for a custom scroll container. Added a ref on `<main>` and an effect resetting its `scrollTop`
to 0 on every `location.pathname` change.

## 9. New "Premium" theme style — added, then made the default (mocked up throughout)

Multi-step feature, each step mocked up and approved before implementing:

- Designed a full alternate look (navy sidebar, ivory/warm-white cards, gold accent, soft shadows)
  across several mockup rounds (dashboard, loan account, cards-with-shadow).
- Added it as a real, selectable **Theme Style** option in Settings > Appearance
  (`theme-provider.tsx`: `ThemeStyle` type/storage/options, mirroring the existing accent/fontSize
  pattern; `index.css`: `[data-theme-style='premium']` CSS variable block; `SettingsPage.tsx`: new
  card with a two-option preview-thumbnail picker). Originally light-only (picking it forced
  `theme` to `'light'`).
- User asked for Premium as the default for everyone, *with* Dark Mode also on — a direct
  contradiction of "light-only." Per the user's own call (offered as a question, not assumed),
  built a proper `.dark[data-theme-style='premium']` dark variant instead of just forcing dark.
  Removed the "Premium forces light" logic from both `setThemeStyle` and a new
  `readEffectiveTheme()` helper — Premium now follows the officer's own Dark Mode preference like
  Classic always has. `DEFAULT_THEME_STYLE` ('premium') + the existing `DEFAULT_THEME` combination
  now gives a never-configured user Premium + Dark automatically.
- User then reported the card shadow looked gone in Premium. Verified it was technically still
  present (`--shadow-card`-equivalent values unchanged at the time) but visually too faint —
  Premium's card/page backgrounds sit closer in lightness than Classic's cooler gray-blue pairing.
  Converted `Card.tsx`'s shadow to a `--shadow-card` CSS variable (overridden per theme-style/mode)
  and strengthened it for both Premium light and dark (mockups approved first for both).
  **Found and fixed a real Tailwind bug along the way**: the first attempt used
  `shadow-[var(--shadow-card)]`, which Tailwind's arbitrary-value heuristic treated as a shadow
  *color* override (producing an empty, invisible shadow) rather than the full `box-shadow` value
  it actually is — caught via computed-style inspection (`boxShadow: "none"`). Fixed with the raw
  `[box-shadow:var(--shadow-card)]` arbitrary-property syntax, which skips that heuristic;
  re-verified the computed shadow matches.
- Finally, user asked to make their *own current* Appearance setup (screenshotted) the default for
  everyone: Dark Mode was actually off (Light) on their account, Theme Color was a custom pick
  (`#dc5d18`, not the Emerald preset) — `DEFAULT_THEME` 'dark'→'light', `DEFAULT_ACCENT`
  'emerald'→'custom', `DEFAULT_CUSTOM_COLOR` '#0f766e'→'#dc5d18'. Text Size, Card Reordering,
  Landing Page, and Dashboard Layout already matched existing defaults — no change needed there.
- Ran a full-app audit afterward (user asked if other pages "look old" by comparison) — checked for
  hardcoded colors bypassing the theme system and plain bordered `<div>`s used instead of the
  shared `Card` component (which would miss the shadow fix). Found the app already consistently
  uses shared, theme-aware components; no broad backlog of un-themed pages to fix.

## 12. Performance — TanStack Query `staleTime`

User asked what could speed up loading / whether caching could help. `staleTime` defaulted to `0`,
so every query refetched on every remount/navigation even when nothing had changed. Set to 2 minutes
globally in `main.tsx`. Doesn't weaken "fresh right after I changed it" — every mutation in the app
already calls `queryClient.invalidateQueries()` on success, which refetches immediately regardless
of `staleTime`; this only skips the automatic background refetch that would otherwise fire from
remounting a page whose data hadn't actually changed.
