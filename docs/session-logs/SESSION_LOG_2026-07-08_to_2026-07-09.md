### Bugs found and fixed along the way

1. **CORS origin mismatch** after moving the frontend to a non-default port — fixed by keeping
   `CORS_ORIGIN` in sync, then standardizing back to default ports.
2. **304 Not Modified misread as a generic error** — `res.ok` is `false` for 304 (only 200–299 is
   "ok"), and a 304 has no body, so `apiClient.ts` was surfacing "Something went wrong" instead of
   using the cached data. Fixed by disabling conditional caching (`cache: 'no-store'`) on every
   API request.
3. **"Unknown borrower" on Loan Accounts** — the page was fetching one independent page of
   borrowers and one independent page of loans; with 4,604 borrowers total, most loans'
   `borrowerId` simply wasn't in that unrelated first page. Fixed by resolving each loan's
   borrower individually by id (`GET /borrowers/:id`).
4. **General API rate limit (300 req/15 min) exhausted during ordinary browsing** — caused by two
   compounding issues: (a) React StrictMode's dev-mode double-invoke of data-fetching effects,
   firing every request twice per real page visit, and (b) the per-borrower lookup fix above
   re-fetching the same borrowers every time a page was revisited. Fixed by (a) adding a
   `didLoadRef` guard against the double-invoke on both list pages, and (b) introducing a shared,
   module-level `borrowerCache.ts` that persists resolved borrowers across page navigations and
   de-duplicates concurrent identical lookups.
5. **"Authentication required" recurring indefinitely** — once a background token refresh failed
   (e.g. the backend's refresh-token reuse-detection revoking a session after several rapid
   test logins), the app had no mechanism to notice and just kept sending unauthenticated requests
   forever, still showing the logged-in UI shell. Fixed by adding an `onSessionExpired` hook in
   `apiClient.ts` that `roleContext.tsx` subscribes to, automatically bouncing the user back to
   the Login page the moment a background refresh fails, instead of leaving the session silently
   broken.
6. **Login rate limit (8 attempts/15 min) exhausted** during repeated testing — not a bug, a
   deliberate brute-force-protection setting from Milestone 6; resolved each time by restarting
   the backend (its rate limiter is in-memory, so a restart clears it) rather than weakening the
   security setting itself.
7. **Docker Desktop / PostgreSQL going down mid-session** (twice) — traced via backend logs
   ("Can't reach database server at localhost:5432"), not a code bug. Restarted Docker Desktop and
   confirmed the `easycash-postgres-1` container's data survived (Docker volumes persist container
   restarts).
