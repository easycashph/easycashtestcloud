## 2. Reverse Payment feature (correcting a wrongly-entered payment)

- User asked why old/migrated payment records can't be reversed. Answer: no `PaymentAllocation`
  breakdown exists for pre-feature payments, by design (see below) — this was accepted, not
  treated as a bug.
- New `PaymentAllocation` model (immutable, one row per transaction×installment, recording exactly
  how much of a payment went to principal/interest/fees/penalty) — `ProcessPaymentUseCase` now
  writes this breakdown alongside every REPAYMENT transaction, giving future reversals something
  precise to undo.
- New `ReversePaymentUseCase` (MIS-only): rejects non-REPAYMENT transactions, already-reversed
  transactions, and transactions with no allocation data (the old-migrated-payment case above), via
  three new domain errors (`TransactionNotReversibleError`, `TransactionAlreadyReversedError`,
  `NoReversibleAllocationDataError`). Negates the original amounts through the *existing*
  `RepaymentInstallment.recordPayment()` / `LoanAccount.applyPayment()` methods — `Money` and the
  installment/transaction component types already tolerate negative amounts, so no new domain
  methods were needed. Commit `cf94109`.
- **Idempotency race found and fixed** (`a937a76`): a real user hit "This loan was just updated by
  another action" while reversing a genuine payment — two near-simultaneous requests both passed
  the "already reversed?" check before either committed. Fixed with `withIdempotency`, keyed by the
  *target transaction ID* (not a fresh random UUID per click, unlike `activate`) — a given
  transaction can only ever be reversed once, so this deterministically catches concurrent/duplicate
  reversal attempts on the same transaction.
- **Misleading error messages fixed** (`e4ffa31`): the frontend's generic error handler treated
  every 409 as "just updated, try again," including the three *permanent* rejections above. Fixed
  by checking `error.code` against a `PERMANENT_REVERSAL_REJECTION_CODES` set first and showing the
  backend's own descriptive message instead.
- Frontend: Reverse button (MIS-only) per not-yet-reversed REPAYMENT row, confirmation dialog
  requiring a reason, "Reversed" badge on already-reversed rows.
- `83431d7`: separately, OR#/AR# were made independently optional on Payment Recording (previously
  OR# was required, blocking entry when only an AR# was available).

## 3. Penalty Calculation engine (ADR-050) — resolves last session's deferral

- User asked how other lending companies compute penalties, then revealed EasyCash's own new
  policy directly: **10% per month, compounded, 3-day grace period**, basis = overdue
  Principal + Interest, no proration of partial months.
- Cross-checked against regulation: BSP Circular No. 1133 (2021) / SEC Memorandum Circular No. 3
  (2022) cap penalties at 5%/month, but only for unsecured, ≤₱10,000-principal, ≤4-month-tenor
  loans. User confirmed EasyCash's actual practice: **5%/month for unsecured loans ≤₱10,000**,
  applied regardless of tenor (all EasyCash loans are unsecured, so this is a pure principal-amount
  tier).
- Explicitly confirmed as a **prospective-only, going-forward policy** — migrated/already-active
  loans keep their existing (static) penalty figures; only brand-new loans from this point on use
  the new engine. This mirrors the LPV-1/LA-4 immutable-snapshot philosophy already used for Loan
  Products.
- User's "apply to all products" instruction forced a design correction mid-session: the tier
  can't live on a per-`LoanProductVersion` config row (a product's principal range can straddle
  ₱10,000, and editing an existing migrated version's `PenaltyRule` would violate the
  immutable-snapshot rule anyway) — it has to be resolved **per loan**, from that loan's own
  `principalAmount`. Implemented as global constants
  (`SMALL_LOAN_THRESHOLD`/`SMALL_LOAN_RATE`/`STANDARD_RATE`/`GRACE_PERIOD_DAYS`) in the presenter,
  not read from `PenaltyRule`.
- `ADR-050-penalty-calculation-formula.md` written (§4 rewritten once, after the "all products"
  correction), `CALCULATION_ENGINE_SPEC.md` §12 flipped UNRESOLVED → CONFIRMED.
- New `PenaltyCalculator` (pure domain service): `wholeCalendarMonthsBetween` anchored at the
  **due date**, not grace-period-end — self-caught a math error before the user ever saw it (the
  worked example only produces 3 whole months when anchored at the due date; anchoring at grace-end
  gives 2, which would have contradicted the ADR's own confirmed example). Formula:
  `overdueAmount × ((1+rate)^monthsLate − 1)` once past the grace window, else zero. 7 unit tests,
  all passing on the first run, including the exact ADR-050 worked example (₱10,000 @ 10%, 3 months
  → ₱3,310.00).
- Wired into `RepaymentInstallmentPresenter` as a live-computed `currentPenaltyOwed` field —
  `null` for migrated loans (`legacyId` set) or PAID installments, a real live figure otherwise.
  Two `RepaymentController` tests broke when the mocked `loanAccount` fixture didn't include
  `principalAmount`/`legacyId` (the presenter threw trying to compare against `undefined`) — fixed
  by completing the mocks. Commit `5d7323f`.
- Frontend: Repayment Schedule table's Fees Due/Penalty Due columns (added last session, then
  static) now show the live-computed value for new loans, the migrated static value otherwise —
  confirmed by the user that migrated accounts' Penalty Due/Fees Due (843/2081 rows with non-zero
  values respectively) genuinely carried over from the old SDevTech system's own computation.

## 8. Loan Document Generation (ADR-051) — first implementation slice

By far the largest piece of work this session. User asked to add generation of loan legal
documents (Disclosure Statement, Promissory Note, and others), viewable once a loan account is
created, using `legacy/Excel LMS Files/Templates/` as the reference — explicitly asking for review
and a recommendation *before* any implementation.

### 8.1 Security fix, found immediately upon opening the referenced folder

`legacy/Excel LMS Files/` (Manual_Checklists PDFs, Saved Loan Documents, SOA — real client PII,
plus the 12 legal Templates) was untracked but **not** covered by `.gitignore` — the same class of
gap found and fixed several times before in this project. Added a rule before touching anything
else; verified via `git status --short`.

### 8.2 Investigation and design (before any code)

- Inspected the 12 `.docx` templates directly (via `unzip`, since neither Word nor LibreOffice is
  installed on this machine) — confirmed none contain programmatic merge-field syntax (no
  `{{}}`/`MERGEFIELD`/`[...]`/`<<...>>`), just labels with blank space for manual typing in Word.
  `DisclosureStatement.docx`'s text matched the real, already-verified SML-REG_00373 disclosure
  statement.
- Presented a recommendation (`docxtemplater` + LibreOffice headless + the existing-but-unbuilt
  local storage abstraction) and an interactive mockup of a "Documents" tab (bulk "Generate all
  required" + individual checkbox selection) — approved by the user before any code was written.
- Asked the user to classify all 12 documents into required-for-every-loan vs. conditional-per-
  product; user confirmed the classification (4 required, 7 conditional-on-Loan-Product, 1 —
  Statement of Account — out of scope, different on-demand lifecycle) and that the user, not this
  tooling, will hand-edit `{Placeholder}` fields into the templates in Word (chosen over having this
  session attempt it programmatically).
- **Major mid-investigation discovery**: while designing the per-product mapping schema, found that
  `DocumentTemplate`/`DocumentTemplateMapping` already existed in Prisma — scaffolded on day one
  (`20260702000000_init`) for a legacy SDevTech/Mambu MongoDB collection (`document_templates`,
  `document_template_mappings`) that looked, at first glance, like a ready-made answer to "which
  document per which product." Investigated directly rather than assuming:
  - 507 `document_templates` rows resolve to only 365 distinct names — a ~7-year (2018–2025)
    accumulation of near-duplicate variants per historical product code and delivery channel
    (`(OLD)`, `DIGISIGN`, `DGTL`, `OTP`, pixel-width variants), not a clean current-state set.
  - `document_template_mappings`' 502 rows reference 49 distinct legacy `loan_product_uid` values —
    **none of which match any of the 44 already-migrated `LoanProductVersion.legacyId` values**
    (verified by direct join, zero matches) — a different/parallel product catalog, not
    joinable without guessing product-code fragments out of template names.
  - Disposition (recorded in ADR-051 §6): **not used as a migration source.** The user's 12 current
    templates remain the sole source of truth; the legacy data is left untouched, for reference
    only. The existing-but-unused `DocumentTemplate`/`DocumentTemplateMapping` tables are repurposed
    (shape changed: `contentHtml`/`isActive`/`legacyId` dropped, `code`/`isRequired`/`sortIndex`/
    `updatedAt` added) for the new design rather than left as dead scaffolding beside new tables.
- `ADR-051-loan-document-generation.md` written covering all of the above plus the generation stack,
  data model, UI, and placeholder naming convention (§8).

### 8.3 Implementation (this session, not yet committed)

- **Schema**: repurposed `DocumentTemplate`/`DocumentTemplateMapping`, added append-only
  `GeneratedLoanDocument` (regenerating never overwrites — a borrower may have already been shown
  or signed an earlier version). Migration `20260712132904_add_loan_document_generation` (built via
  `prisma migrate diff` against the live dev DB + manual folder, since `prisma migrate dev` needs an
  interactive terminal not available in this session). Seeded the 11 in-scope `DocumentTemplate`
  rows in `prisma/seed.ts`.
- **File storage abstraction implemented for the first time** — `Attachment.storageKey` and
  `STORAGE_DRIVER`/`STORAGE_LOCAL_PATH` env vars existed since early in the project, but no actual
  storage code existed anywhere (the frontend's Attachments panel has honestly labeled real file
  storage "Coming Soon" this whole time). New `IFileStorage` port + `LocalFileStorage` adapter.
- New `loan-document` backend module (Clean Architecture: domain/application/infrastructure/
  interface), including:
  - `LoanDocumentMergeDataResolver` — builds the `{Placeholder}` → value map from the loan account,
    borrower, loan product, branch, and repayment schedule.
  - `numberToWords.ts` — spells out peso amounts for `{LoanAmountWords}` (Promissory Note/Deed of
    Assignment convention), reimplemented rather than reusing the legacy Mambu template engine's
    `IN_WORDS_INTEGER`/`IN_WORDS_FRACTIONAL` functions (not migrated, per §8.2's disposition).
  - `DocxtemplaterDocumentFiller` — fills a `.docx`'s placeholders (docxtemplater + pizzip).
  - `LibreOfficeDocxToPdfConverter` — shells out to headless `soffice`.
  - `GenerateLoanDocumentUseCase` (gates on loan status APPROVED/ACTIVE/ACTIVE_IN_ARREARS, and on
    conditional-template-applicability via `DocumentTemplateMapping`), `ListLoanDocumentsUseCase`,
    `GetGeneratedLoanDocumentFileUseCase`.
  - HTTP layer (generate/list/download endpoints), wired into `app.ts`.
- **LibreOffice added to `backend.Dockerfile`** (`apk add libreoffice`, ~600MB) — not installed on
  this Windows dev machine, so the PDF-conversion step could not be tested end-to-end locally; the
  docx-filling step has no such dependency and was fully unit-tested (11 new tests: `numberToWords`,
  `DocxtemplaterDocumentFiller` against a synthetic in-memory `.docx` fixture, and
  `GenerateLoanDocumentUseCase` with mocked ports). Full backend suite: 584 tests passing, nothing
  broken.
- **Frontend**: real "Documents" card added to `RealLoanDetailView` on the Loan Detail page (the
  API-backed view, distinct from the hand-authored-mock `LoanDetailPage`/`AttachmentsPanel` path —
  the mockup's tab design was adapted to a stacked-Card layout to match this page's actual existing
  pattern, since it doesn't use tabs). "Generate all required," per-row checkbox + "Generate
  selected," Download (a new `apiClient.downloadFile()` helper, needed because the existing
  `apiClient` only handles JSON responses, not binary blobs with an Authorization header).
- **Verified live in the browser** against a real, non-mock APPROVED loan (`SML-REG_00174`):
  Documents card renders all 4 required documents correctly; clicking "Generate" reaches the
  backend and returns the exact intended error — `"The template file for "DISCLOSURE_STATEMENT" has
