## 7. Cross-site refresh-cookie bug (Cloudflare Tunnel + Pages)

User report: gets logged out of the LMS every ~15 minutes when accessing it via the Cloudflare
Tunnel (`*.trycloudflare.com` backend + `easycash-lms.pages.dev` frontend on Cloudflare Pages).

Root cause: the refresh-token cookie was a blanket `SameSite=Strict`. The Pages frontend and the
tunnel backend are genuinely different sites (different eTLD+1), so the browser never sends that
cookie on the cross-site `/auth/refresh` call — CORS was already correctly configured, but SameSite
is a browser policy independent of CORS. The app's existing silent-refresh logic
(`apiClient.ts`'s `refreshAccessToken()`) was therefore always failing, forcing a full relogin the
moment the access token expired.

Fix (`cookies.ts`): cookie attributes are now decided per-request from the `Origin` header, not a
static `NODE_ENV` flag (this same backend serves both plain-HTTP local dev and the cross-site
tunnel at once, so one static setting can't be correct for both). A known local-dev origin
(localhost/127.0.0.1/private-LAN, same pattern as the CORS dev-origin regex) keeps
`SameSite=Strict` (tightest CSRF protection, works over plain HTTP); any other origin (the
Cloudflare Pages domains already in `CORS_ORIGIN`) gets `SameSite=None` + `Secure`. Also bumped
`JWT_ACCESS_TTL` from `15m` to `1h` as an extra buffer (`.env`, not committed — `.env.example`
only). User must log out and back in once via the tunnel URL to pick up a cookie under the new
policy; not independently verified live (no login credentials in this environment).

## 9. Roles & Permissions (largest piece of this session)

### Request and design

User: MIS should be able to configure per-role access (e.g. a Collection Officer role should NOT
have Record Payment, Documents, or E-Signature access), with a "high-end, advanced" UI. Investigated
current state first: `Role`/`Permission`/`RolePermission` tables have existed unused since
Milestone 6 (AUDIT-3); actual enforcement was `requireRole(...)`, hard-coded per-route allow-lists
(ADR-043's deliberate interim measure — ADR-038's full design was explicitly deferred, "likely its
own milestone"). Also found `document.generate` and `esignature.manage` had **no role restriction
at all** — any authenticated user could already do both, which was the user's concrete motivating
example. Built and showed a mockup (role list + per-module permission-toggle matrix, teal/dark
theme) before implementing, per this session's established "mockup first" pattern.

### Permission taxonomy (27 codes)

Confirmed with the user, then seeded in `prisma/seed.ts` with default `RolePermission` grants that
mirror every route's exact pre-existing `requireRole` allow-list (or, for the 4 previously-open
routes, default to every role — preserving prior behavior). This migration changed nothing about
who could do what on day one; it only made it configurable going forward.

### Backend

- New `requirePermission(code)` middleware (`shared/middleware/requirePermission.ts`) — live
  `RolePermission` DB lookup, imports the shared `prisma` singleton directly (same pattern as
  existing repositories) rather than being threaded through every router's DI constructor.
- Replaced `requireRole(...)` with `requirePermission(code)` across every router that had one:
  `loanAccountRouter`, `borrowerRouter`, `documentRouter`, `loanDocumentRouter` (new gate),
  `loanSigningRouter` (new gate), `repaymentRouter`, `loanApplicationRouter`, `loanProductRouter`,
  `aiExtractionRouter`, `paymentReminderRouter` (new gate), `profileNoteRouter` (new gate),
  `reportingRouter` (new gate), `auditLogRouter`, `userRouter`, `reminderSettingsRouter`,
  `ProfileActivityLogRouter`.
- New `access-control` module (Clean Architecture: port, 2 use cases, Prisma repository,
  controller, router, presenter) — `GET /roles-permissions`, `PATCH /roles/:roleId/permissions`

- `tests/unit/authorization.test.ts` (the router-wiring H-3 suite) updated to mock
