### Bug found and fixed: scheduled runs were silently failing since 2026-08-10

While checking backup progress on 2026-08-12, found every scheduled 9 AM run since 2026-08-10 had
failed: `didn't find section in config file ("gdrive")`. The config file
(`C:\Users\EASYCASH\AppData\Roaming\rclone\rclone.conf`) exists and works fine from an interactive
shell, but rclone's default config-path resolution wasn't finding it under Task Scheduler's
execution context (task runs as the same user, `LogonType: Interactive`, but env/profile
resolution still differed enough to break the lookup).

**Fix**: pass `--config` explicitly in `backup-to-google-drive.ps1` instead of relying on rclone's
auto-discovery. Verified by manually triggering the scheduled task (`Start-ScheduledTask`) and by
reproducing the exact same invocation the task uses (`Start-Process powershell.exe -File ...`) —
both completed a real 9-minute sync of all 55 changed files, only tripping on one transient
single-file md5 mismatch (unrelated, self-heals on the next incremental sync). Committed as
`76eb20c`.

### Disclosure Statement (and other generated documents) — comma-formatted amounts

User: "lagyan mo rin ng comma ang mga amount sa Disclosure Statement katulad ng ginawa mo sa SOA."

`LoanDocumentMergeDataResolver.ts` (shared by every DOCX template, not just the Disclosure
Statement) was emitting raw `Money.toString()` figures ("3806716.2") with no thousands separator.
Added a `formatMoney()` helper mirroring the one already added to
`StatementOfAccountMergeDataResolver.ts` on 2026-08-06, and applied it to every money field
(`PrincipalAmount`, `ProcessingFee`, `NetProceeds`, `TotalPaymentDue`, the whole
`AmortizationSchedule`/`Schedule` tables, etc.). Deliberately not a change to `Money.toString()`
itself (used elsewhere for persistence/API payloads that must stay machine-parseable) —
comma-grouping is print-display-only, scoped to this resolver's merge data, same reasoning as the
SOA fix. Since the resolver is shared, every other generated document (Promissory Note, etc.) now
gets comma-formatted amounts too, not just the Disclosure Statement.

Verified live: generated a real Disclosure Statement PDF for an actual APPROVED loan account via a
one-off script instantiating the real use case, rendered it through
`LibreOfficeDocxToPdfConverter`, and read the resulting PDF — confirmed `3,806,716.20` and the full

## 3. New feature: editable ATM/mitigation details after a loan is decided

`LoanApplicationDetailPage.tsx`'s Underwriting card was editable only while the application was

**Backend** — generalized the existing account-owner-only pattern:

  `SET_MITIGATION_DETAILS`.
- `PATCH /loan-applications/:id/mitigation-details` (new route, same `loan_application.manage`
  gate as every other mutation on this router, deliberately not status-gated like

## 4. Bug fix: reversed payment left a stale Paid Date

User reported: after reversing a payment on a Repayment Schedule, the "Paid Date" column still
showed the old date even though every Amount Paid column read "—".

Root cause: `RepaymentInstallment.recordPayment()` already had a 2026-08-07 fix that correctly
clears `lastPaidAt` to `undefined` once an installment is reversed back to zero. But
`PrismaRepaymentInstallmentRepository.ts`'s `toUpsertData()` passed that `undefined` straight into
the Prisma `update`/`create` `data` object as `lastPaidAt: installment.lastPaidAt` — Prisma
silently **skips** `undefined` fields in a write payload instead of clearing the column to `null`,
so the domain-layer fix never actually reached the database. Every other nullable override field in
that same function (`penaltyOverrideAmount`, `feesOverrideAmount`, etc.) already used the `?? null`
pattern; `lastPaidAt` was the one field that didn't.

**Fix**: `lastPaidAt: installment.lastPaidAt ?? null`. Committed as `5c6d3cd`.

**Live-data cleanup**: found the exact affected record — loan `SML-Self_00058`, installment #1
(`repaymentSchedule.id = b4109288-8313-4aae-aacd-15a71a1a35bf`), `principalPaid`/`interestPaid`
both `0` but `lastPaidAt` stuck at `2026-08-10T06:26:56Z`. Per the user's established
confirm-before-backfill preference, asked and got explicit go-ahead ("oo, i-fix mo na") before
correcting it — a one-off script re-verified `principalPaid`/`interestPaid` were still exactly zero
(safety check) before clearing `lastPaidAt` to `null` directly via Prisma. Not part of the code
commit (a live-data correction, not a code change).
