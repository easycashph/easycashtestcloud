2. **Loan Application Review Pipeline — "Under Review" / "Pre Approval" stages** (the major piece
   of this session). The user described their real-world process: Requirement Compliance (system
   pass/fail) → manual Review (CI, Credit Bureau checking, document checking by CRM/credit risk
   mgmt, producing a report) → Pre Approval tag → final Approve (Manager-level only) → Create
   Client Account. The existing system only had a two-step pipeline (system PREAPPROVED/
   PREDECLINED → direct officer Approve/Decline, no role distinction). A mockup was shown and
   confirmed before any planning; a formal plan (via `EnterPlanMode`/`ExitPlanMode`, backed by an
   `Explore` investigation and a `Plan` agent) was written and approved before implementation,
   split into 4 approvable milestones per CLAUDE.md's "work incrementally" rule:

   - **Milestone A (schema + domain, no behavior change):** added `UNDER_REVIEW`/`PRE_APPROVAL` to
     `LoanApplicationStatus`, a new `CreditBureauResult` enum, and 5 new `LoanApplication` fields
     (`reviewStartedByUserId/At`, `reviewReport Json?`, `preApprovedByUserId/At`) via hand-written
     migration `20260716120000_add_loan_application_review_stages`. Domain gained
     `startReview()`/`updateReviewReport()`/`tagPreApproval()`; `decline()` widened to accept
     PREAPPROVED/PREDECLINED/UNDER_REVIEW/PRE_APPROVAL; `approve()` deliberately left unchanged
     (still worked directly from PREAPPROVED/PREDECLINED) so nothing broke mid-rollout. 13 new
     unit tests.
   - **Milestone B (use cases + API, still backward-compatible):** `StartLoanApplicationReviewUseCase`,
     `SubmitLoanApplicationReviewReportUseCase`, `TagLoanApplicationPreApprovalUseCase`; new routes
     `POST /start-review`, `PATCH /review-report`, `POST /tag-pre-approval` (same 3-role access gate
     as before); presenter/schema/repository updated for the new fields. 13 more tests. Backend
     Docker image rebuilt and verified live.
   - **Milestone C (the breaking change):** narrowed `approve()` to PRE_APPROVAL-only, and
     restricted the `/approve` route to `requireRole('MIS', 'Loan Operation Manager')` — CRM can no
     longer give the final approval, matching the confirmed requirement. Checked live data first:
     only 1 application was PREAPPROVED at cutover (low risk). Added regression tests confirming
     `approve()` now throws from PREAPPROVED/PREDECLINED/UNDER_REVIEW and only succeeds from
     PRE_APPROVAL. Docker rebuilt again; confirmed all 4 new routes registered (401, not 404)
     against the live container.
   - **Milestone D (frontend):** new shared `loanApplicationStatusLabels.ts` (PREAPPROVED →
     "Requirement Compliance", PREDECLINED → "Pre Declined", plus the two new statuses) used by
     both `LoanApplicationsPage.tsx` and `LoanApplicationDetailPage.tsx`. `roleContext.tsx` gained
     `canReviewLoanApplication` (MIS/Loan Operation Manager/CRM) and `canApproveLoanApplication`
     (MIS/Loan Operation Manager only). Detail page gained a new `ReviewReportCard` (CI notes
     textarea, Credit Bureau result/score, and a document checklist sourced from the application's
     own `submittedDocuments` array rather than an invented static list), new mutations
     (`startReviewMutation`, `tagPreApprovalMutation`), and the decision-button section split into
     4 stage-specific branches (PREAPPROVED/PREDECLINED → Start Review + Decline only, no direct
     Approve; UNDER_REVIEW → Review Report + Tag Pre Approval + Decline; PRE_APPROVAL → read-only
     report + role-gated Approve + Decline; APPROVED/DECLINED → unchanged decided-state panel).

   All 4 milestones committed together as `d9c66a5` once Milestone D was verified (`tsc --noEmit`
   clean both sides; backend suite at 683 passed / 16 pre-existing failures, no regressions; no
   browser click-through was possible — no login credentials available in this environment, a
   constraint noted throughout this whole multi-day session — verified via `tsc`, unit tests, and
   direct route-registration checks against the live backend container instead).

   **Deliberate scope decision, flagged to the user rather than invented:** no "completeness rule"

6. **Loan origination fee data-completeness investigation and 3-round backfill** — user asked why
   Processing Fee (and other origination fees) showed 0.00 for most loans in the Loan Releases
   Report. Investigated thoroughly rather than assuming a code bug:
   - Verified via a direct repository call + real generated `.xlsx` inspection that the report *code*
     was correct — fees genuinely were 0 in the database for the vast majority of loans.
   - Root cause: the origination fee fields on `LoanAccount` (processingFee, advanceInterestFee,
     accountManagementFee, insuranceFee, notarialFee, webFee, docStampFee,
     outstandingBalancePayoff) were added 2026-07-11 for **new** loans created through the in-app
     Create Loan Account form only — never backfilled during the CP12 legacy migration. Confirmed
     via both the live DB and a restored 2026-07-14 PostgreSQL snapshot the user provided
     (`legacy/db-exports/easycash_2026-07-14.dump`, restored into a scratch `dump_check` database via
     `docker cp` + `pg_restore`, dropped after use): all 1,783 legacy-migrated loans were 0 across
     every fee column in both snapshots; only the 7 loans created after migration had real values.
   - **Round 1** (`a0b5b7f`, script `backfill-loan-origination-fees.ts`): matched the legacy Excel
     LMS's `Loans_details` sheet (`legacy/reports/BETA 1.5.83 LMSv3.xlsm`, 260 rows) by loanCode —
     136 of 260 backfilled (only loans currently all-zero were touched; 6 were zero in the source
     too; 118 had no matching loanCode). Full 136-row preview shown to the user via an Artifact
     before applying.
   - **Round 2** (`b8a13bd`, script `backfill-loan-origination-fees-mongo.ts`): user reported
     `SML-REG_00372` still had no fees after Round 1 — investigated and found it was disbursed after
     the personal Excel's own cutoff (May 28, 2026). Found a much wider, more authoritative source
     instead: the real SDevTech production `monthly_loan_releases` MongoDB collection
     (`legacy/MongoDB dump/.../db-easycash/monthly_loan_releases.bson`, parsed directly via the
     `bson` npm package — 3,710 docs / 1,231 unique loans, disbursement dates 2009 through
     2026-07-01). Backfilled 451 more loans (593 of 1,790 loans now have real fee data). Idempotent —
     re-running reports 0 to apply.
   - **Round 3** (`9063196`, script `backfill-loan-origination-fees-inferred.ts`): user asked about 4
     more specific loans still at 0 (`SML-QC_00027`, `SML-REG_00377`, `SML-REG_00376`,
     `SL-REG_00117`) — all disbursed after `monthly_loan_releases`'s own July 1 cutoff too. Dug into
     the raw `loan_transactions` collection (type=`FEE_CHARGED`), joined via
     `loan_accounts._id == loan_transactions.parent_account_key` — found real per-transaction dollar
     amounts for 3 of the 4, but with no fee-type label on the source records. Inferred the mapping
     (largest = Processing Fee, second-largest = Account Management Fee at an exact 10-12.5% ratio,
     the two constant-500 amounts = Notarial/Web Fee, remainder = Insurance Fee) from a pattern
     confirmed *exact* (not approximate) across all 3 loans and consistent with the 593
     already-backfilled loans — flagged explicitly to the user as inferred rather than
     explicitly-labeled, per CLAUDE.md's Confirmed/Assumed distinction, before applying.
     `SML-QC_00027` genuinely had no `FEE_CHARGED` transactions at all (still `PENDING_APPROVAL` in
     the Mambu snapshot) — correctly left untouched.
   - **Manual entry** (`8397fe8`, script `backfill-loan-origination-fees-manual.ts`, documentation
     only): user asked specifically about `SML-QC_00027`'s missing Notarial Fee. Exhaustively
     cross-checked *every* collection in the MongoDB dump (`activities`, `custom_field_values`,
     `repayments`, `attachments`, `generated_loan_documents`, `loan_notes` — even re-checked the
     already-restored `easycash_2026-07-14.dump` PostgreSQL snapshot directly) plus the Excel LMS
     again — confirmed no source record exists anywhere; the loan's own product config
     ("SML-Quick Cash") even marks Notarial Fee as `NONE`. User explicitly confirmed it should be
     ₱500.00 anyway (the standard flat amount on nearly every other SML loan) and asked for it to be
     entered directly — a manual business decision, not a data-recovery finding, applied and
     documented as such rather than silently treated as "found."
   - Confirmed with the user that new loans going forward need no backfill — verified the 7
     non-legacy loans in the live DB already have Notarial/Web/Insurance/Account Management Fee
     populated correctly at Create Loan Account time (Processing Fee alone is often left 0 by staff
     on the form — flagged as a possible follow-up, not yet acted on).
